# ADR：用 Tauri 2 构建离线制图客户端

状态：已采纳。提案：2026-11-20（UTC+08:00）；采纳：2026-11-20 10:59 +08:00。范围：在 `tongcraft-map` 新建独立制图客户端，不修改游戏启动器。本决定替代[原技术栈提案](2026-11-20-offline-map-stack.md)中仅以 CLI 为本地入口的设计，不代表该提案的其他待定项已获验证。

## 决定

- 桌面端使用 Tauri 2 + TypeScript。WebView 只负责选择存档、配置维度与输出目录、开始或取消任务、显示进度和预览结果。
- 桌面端与独立 CLI 直接调用同一 Rust 渲染库；核心不依赖 Tauri 或窗口。桌面端在后台任务中调用核心，跨 WebView 的是控制命令、进度和结果信息，不是逐瓦片 RGBA 数据。CLI 供 CI、定时任务和性能对照使用。
- 保留 CPU 参考后端，并提供原生 `wgpu` 硬件计算后端。桌面预览通过与公开网站相同的 Leaflet 视图读取生成好的静态瓦片；公开网站不打包 Tauri，也不要求 WebGPU。

## 取舍与重议条件

MyGo + 独立 Rust 渲染器提供进程隔离，但对新项目意味着两套原生工具链、子进程协议与配套分发。全 Go + MyGo 可以避免跨语言协议，但若坚持原生 Rust `wgpu`，仍需解决绑定或进程边界。因此选择 Tauri 是为了共享核心和预览，而不是假设 Tauri 能加速渲染。

代价是客户端依赖系统 WebView；后台任务能避免阻塞界面，却不能隔离原生崩溃。若实际出现驱动崩溃拖垮界面或任务必须独立恢复，再评估用已有 CLI 作子进程，不改变瓦片协议。

验证顺序：先用 CLI 在实际渲染机上比对同一小片世界的 CPU/GPU 像素和端到端耗时，再用桌面端完成一次选档、渲染、预览及取消。取消不得发布半成品。未完成实机验证前，不承诺 GPU 加速倍率，也不默认 GPU 一定优于 CPU。
